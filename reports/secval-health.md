# secval health report (2026-10-18)

App: secval.onrender.com. Rated from the code (1903978-prog/anti-hacker, integration, commit d7d109c) and what was checked in this thread. Everything here is an **estimate**, and anything not checked is marked "not verified".

| Area | Score | Why |
|---|---|---|
| Security & Access Control | ~90 | Checked in code and tests: every API call, reads included, needs the secret token (compared in constant time; refused if none is configured). The web page signs in once and gets an HttpOnly, Secure, SameSite=Strict cookie, and changes made with that cookie must come from secval's own page. Wrong tokens are capped at 10 a minute across all callers, while the right token always works. Plus a 120/min rate limit, strict headers and CSP, a fail-closed policy gate before every scan, an append-only audit trail and a kill switch. Held back: one owner token rather than named accounts with two-step login. |
| Data Protection & Privacy | ~90 | Scans keep only findings, never site data. The allowlist, audit trail, scans and dashboard need sign-in, API answers are marked not to be cached, and the token is no longer stored in the browser (page scripts cannot read the sign-in cookie). Held back: domains waiting for proof are remembered in browser storage. |
| Data Integrity & Consistency | ~75 | Input is validated (zod), multi-row writes use transactions, and database triggers block edits to the audit log. Held back: there are no schema migrations, so a new column on an existing table would not appear on an old database. |
| Data Persistence & Recovery | ~80 | Litestream copies the store to Backblaze B2 about every second and restores it when Render starts a fresh machine. Restore is proven: ownership proofs for compplan, lm-op-model and nexus survived the 18/10 redeploy (Livio's screenshots). Built in code: a daily restore test copies the backup into a scratch file and checks it is intact, with the result and a "Test restore now" button under Settings and in the audit trail; 7 days of history are kept; a failed restore at start is shown as a warning instead of passing silently. Held back: one backup location only, the last second of changes can be lost on a sudden wipe, and the daily test is not yet seen passing live. |
| Database Design & Structure | 65 | 1 One master database: 10/10 (one SQLite file; the Backblaze copy is only a backup); 2 No duplicated data: 5/10 (each changed report is stored again in full, findings_count repeats a count of findings, host is copied onto every score row); 3 Links between records: 5/10 (findings link to scans and scores to reports with enforced foreign keys, but scans, uptime checks and reports name the app as text with no link to the allowlist); 4 Unique IDs and rules: 5/10 (every table has a primary key and not-null rules; no database rules on status, mode or the 0-100 score range, only checks in the code); 5 Versioned schema changes: 0/10 (tables are created with CREATE IF NOT EXISTS in server/db.ts; no migrations); 6 Backups and proven restores: 10/10 (Litestream streams to Backblaze B2; proofs survived the 18/10 redeploy per Livio's screenshots); 7 Indexes on main lookups: 5/10 (one index, uptime checks by app and time; none on findings by scan or scores by app); 8 Sensitive data protected: 10/10 (no passwords stored, the token lives in settings, scans keep findings not site data); 9 No secrets in code: 10/10 (database path and backup keys come from environment settings, litestream.yml); 10 Clear naming and documented schema: 5/10 (one snake_case style and comments in server/db.ts, but no written schema document) |
| User Experience & Interface | ~72 | One page with no pop-ups. The dashboard table was checked at desktop and phone width (390 px) with sample data. Held back: one long page, and the phone needs sideways scrolling for the table. |
| Performance & Scalability | ~60 | One instance with SQLite and an in-memory rate limit. That's fine for one user. Free-tier cold starts are slow (time not measured). |
| Reliability & Error Handling | ~60 | Scheduler and uptime errors are caught so they never crash the server. Held back: the timers run inside the app, so when the free tier sleeps the weekly scan and uptime checks stop. The UptimeRobot pinger that keeps it awake is not verified. |
| Code Quality & Maintainability | ~80 | Type check is clean, 98 of 98 tests pass locally, and the modules are small, each with one job. |
| Deployment & Operational Readiness | ~45 | No CI runs (PR #6 had 0 checks). There are two GitHub copies, and Render builds from the old one, so changes have to be copied by hand. |
